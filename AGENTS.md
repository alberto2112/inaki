# AGENTS.md — Inaki

Multi-agent AI assistant with hexagonal architecture, RAG memory, scheduling, and agent delegation.

> `CLAUDE.md` is the canonical guidance file and carries the full rule set. This file is
> the condensed version for other agents. When they disagree, `CLAUDE.md` wins.

```

ruff check .                     # lint
```

## Architecture — a modular monolith under `inaki/`

```
inaki/
  shared/         ← Domain primitives every module may use: Message/Role, attachment grammar,
                    ChannelContext, errors, skip marker. Imports NOTHING from the project.
  kernel/         ← The turn: RunAgentUseCase, tool loop, ConversationHistory, the ports it
                    consumes (domain/, ports/, use_cases/). Never imports a feature module.
  observability/  ← Logging, debug mode, turn traces (ITurnTracer), startup events
  config/         ← Schema (one section per area), 2-layer YAML loader + migrations, merge
                    engine, instance home, effective-config use cases, `config` tool, web UI
                    backend (wiring.py), error boundary
  llm/            ← LLM providers (PROVIDER_NAME discovery) + wiring.py
  embedding/      ← e5_onnx / openai providers, cache, model download + wiring.py
  memory/         ← history store, semantic memory, consolidation, reconciliation, tools + wiring.py
  knowledge/      ← RAG over documents: sources, orchestrator, tools + wiring.py
  skills/         ← YAML skills repo + wiring.py
  tools/          ← ITool/ToolResult, ToolRegistry with semantic routing, builtin tools,
                    tool-config store + wiring.py
  extensions/     ← Discovery of user extensions (`<home>/ext/*/manifest.py`)
  scheduler/      ← Harness-global tier: domain (cron), ports, service, SQLite repo, dispatch
                    adapters, the `scheduler` tool split per operation + wiring.py
  agents/         ← Delegation (`delegate` tool, background queue), scope dispatcher,
                    scope registry, ephemeral child + wiring.py
  perception/     ← Photos, faces, scene description, transcription (channel-independent) + wiring.py
  channels/       ← One package per channel, each implementing IChannel + IChannelOutbound:
    telegram/     ← bot (composed collaborators), outbound (the transport EDGE), broadcast, files, config
    rest/         ← Admin API (FastAPI) + the config web UI page
    cli/          ← Interactive chat runner
  app/            ← Composition root: assembly.py (five explicit passes → immutable
                    AgentRuntime/HarnessRuntime), settings.py (config → Settings VOs),
                    bootstrap, runner, reloader, extensions registration
  cli/            ← Entry points, one module per command (init, service, chat, daemon,
                    admin, tool, send, scheduler, knowledge) + `_common`
main.py           ← Compat wrapper for systemd units generated by the old install.sh
```

**Dependency direction**: `composition root (inaki/app, inaki/cli) → modules → kernel`. Never reversed.

The law between packages is `[tool.importlinter]` in `pyproject.toml`, verified by
`lint-imports` (15 contracts). In words:

- `kernel` knows only `shared` (plus the third-party allowlist `pydantic`, `croniter`, `numpy`,
  guarded as a ratchet by `tests/kernel/test_terceros_del_kernel.py` — `DEUDA_*` lists stay empty).
- `shared` and `extensions` know nobody in the project.
- Every feature module knows the kernel and `shared`; `memory`, `knowledge`, `skills` and `tools`
  may also know `embedding`. `memory`/`knowledge`/`skills` are independent of each other.
- A module's `wiring.py` is the ONLY file in that module allowed to import `inaki.config`
  (declared as `ignore_imports` in its contract) and to call another module's `wiring.py`.
- A channel never imports `inaki.app` or `inaki.cli`; channels are independent of each other.
- `inaki/app` and `inaki/cli` may import everything — assembling is their job.

Never fix a violation with `ignore_imports`: use a Settings VO, a structural Protocol, or move
the wiring to the composition root.

**Three structural rules** — read `docs/arquitectura.md` before adding a channel or a stateful resource:

1. **Thin channel** — a capability is implemented ONCE (use case in its module) and exposed via
   an LLM tool plus the single admin gateway (`POST /admin/tool/invoke`, client `inaki tool`).
   A channel only translates its native I/O into a turn. Never re-implement a capability per
   channel. `docs/arquitectura.md` has the step-by-step "how to add a channel".
2. **Resource tiers** — harness-global singletons (`knowledge`, `scheduler`, `faces`) live in
   `GlobalConfig` and the `HarnessRuntime`; per-agent resources (`memory`, `history`,
   `channels`, `llm`, `embedding`) live in `AgentConfig` and each `AgentRuntime`. Never a third
   ad-hoc pattern. Isolation of a global resource = another harness process with its own `--home`.
3. **Wiring** — each module assembles itself in its `wiring.py`; use cases receive Settings VOs
   (`inaki/kernel/domain/value_objects/agent_settings.py`, mapped in `inaki/app/settings.py`),
   never `AgentConfig`. Provider modules own their `Resolved*Config` DTOs.

## Configuration System

Config lives in `~/.inaki/` (the instance home; `--home DIR` / `INAKI_HOME` relocates it whole).
`inaki init` writes it; the first run of any command bootstraps `global.yaml` from the schema
defaults if it is missing.

**2-layer merge** (each layer completes or overrides only what it declares):
1. `~/.inaki/config/global.yaml`
2. `~/.inaki/agents/{id}.yaml` (sub-agents in `agents/sub-agents/`)

Credentials live in those same files (mode `600`, gitignored). A field is secret by its mark in
the schema (`secret: True`), not by the file it is written in. `config/tool_config.yaml` is
daemon-owned and does not take part in the merge. Unknown keys abort startup: never remove or
rename a schema field without a loader migration.

Inspect and edit: `inaki config show --origin` (effective config with the layer each value comes
from) and `inaki config web` (same view, editable per layer, validated with the startup loader;
also served by the daemon at `/admin/config/ui`).

## LLM, Embedding & Transcription Providers

All three are auto-discovered by scanning a package for a module-level `PROVIDER_NAME`
constant. The three registries are **independent** — being available as an LLM does not make a
vendor available for transcription.

- **LLM** (`inaki/llm/`): `anthropic`, `custom`, `deepseek`, `groq`, `ollama`, `openai`,
  `openai_responses`, `openrouter`. The OpenAI-dialect ones share `OpenAICompatibleProvider`.
- **Embedding** (`inaki/embedding/`): `e5_onnx` (local ONNX, downloaded by `inaki init`) and
  `openai`. Dimension is 384 — changing it requires dropping and recreating the memory DB.
- **Transcription** (`inaki/perception/adapters/transcription/`): `groq`, `openai`.

Add a provider by dropping a module in the right package with `PROVIDER_NAME = "{name}"`.

## Memory & History

SQLite databases under `~/.inaki/data/` (paths are `RuntimePath`, anchored to the instance home):

- `inaki.db` — long-term memory with `sqlite-vec` embeddings
- `history.db` — chat history + `agent_state` + face metadata side-table
- `scheduler.db` — scheduled tasks and run logs
- `faces.db` — face embeddings FLOAT[512] (created on first use)
- `embedding_cache.db` — embedding cache

Consolidation extracts memories from chat history via LLM, embeds them, stores them in the
vector DB, then writes a markdown digest per `(channel, chat_id)` scope.

## Agent Delegation

`inaki/app/assembly.py` builds every agent draft in pass 1 and wires delegation (the `delegate`
tool) in pass 3, once ALL agents exist. Each delegation builds an **ephemeral one-shot child
resolved against the CALLER** (`inaki.agents.wiring.build_ephemeral_child`): the child inherits the
caller's `llm` by default and operates with the caller's tools/resources, narrowing the visible
subset via `tools.allowed`. `delegate` is async by default (`wait=false`): it queues and returns
`bg-N` immediately. Recursion prevention is structural: `delegate` is filtered from sub-agent
schemas.

## Extensions

User extensions live in `<home>/ext/` (`app.ext_dirs`). Each extension needs a `manifest.py`
exposing `TOOLS` (list of classes) and `SKILLS` (list of relative file paths); the contract is
`from inaki.tools import ITool, ToolResult, IToolConfigStore`. Registration happens in
`inaki/app/extensions.py`.

## Testing

- `pytest-asyncio` mode is `"auto"` — no `@pytest.mark.asyncio` needed
- Fixtures in `tests/conftest.py`: `agent_config`, `mock_llm`, `mock_memory`, `mock_embedder`,
  `mock_skills`, `mock_history`, `mock_tools`; `tests/app/conftest.py` has the assembler fakes
- Golden-path tests in `tests/integration/golden/` patch the provider factories
  (`inaki.llm.wiring.LLMProviderFactory.create`, `inaki.embedding.wiring.EmbeddingProviderFactory.create`)
- `tests/config/test_config_docs_drift.py` fails if the generated config docs drift from the schema

## Code Conventions

Variables, docstrings, comments and error messages are **in Spanish**. Tool `description`
fields are in English (LLM comprehension); `routing_keywords` are multilingual es/en/fr.
Tool results are always `ToolResult` objects. Message roles use the `Role` enum.
Config parameters are documented ONLY in their schema docstring (the docs are generated from it).

## Change Workflow (SDD)

Substantial changes go through the `sdd-*` skills: explore → proposal → spec → design →
tasks → apply → verify → archive.

Artifacts are stored in **engram** by default (no files created). The file-based
`openspec/` store is opt-in and **not currently present in this repo** — do not assume
`openspec/changes/` exists.

## Production Target

Raspberry Pi 5 (4GB RAM, ARM64) via systemd. Install with `pipx install "git+https://github.com/alberto2112/inaki"`,
then `inaki init` and `inaki service install` (the unit is generated from the package;
`MemoryMax=2G`). Config and data under the instance home (`~/.inaki/` by default).

RAM footprint, ARM64 and token cost are first-class constraints — not afterthoughts.

|---|---|
| Language | Python 3.11+ |
